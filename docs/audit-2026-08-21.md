# Consistency audit — 21 Aug 2026

What the documents claim, against what the repository contains and what the Google Cloud
project actually has deployed. Branch `google-sign-in`, project `warrent-505918`.

**Method.** Every finding below was checked, not inferred. Test suites and builds were run;
the deployed state was read from the live project with `gcloud` and the Firebase Rules REST
API. Where something could not be run on this machine it is marked as unverified rather than
asserted.

## A. Claimed in shipped documents, absent from the code

These matter more than ordinary drift because `STRATEGY.md` §2 records that judges *"are not
required to test the Project and may choose to judge based solely on the text description,
images, and video."* Every item here is a claim a judge could check by opening the repo.

### A1 · The MCP server does not exist

`README.md` lists seven MCP tools under *For other systems* and states:

> **Our own dashboard is an MCP client** — it reads and acts through the same surface any
> external caller uses, so this is load-bearing rather than aspirational.

`docs/architecture.md` §9 repeats it, §11 lists *"MCP server on Cloud Run, consumed by our own
dashboard"*, and §8 names *"MCP requests from external callers"* as a Model Armor surface.

There is no MCP code anywhere in the tree. `grep -ri mcp` over `web/src`, `agents`, `android`
and `contract` returns nothing; the only hits in the repo are seed data and `package-lock.json`.
None of `list_procedures`, `open_job`, `step_status`, `get_record`, `inventory`, `raise_po` or
`request` is defined.

`STRATEGY.md` §6 puts "MCP surface" second in the cut order, so this was a deliberate cut. The
cut was never reflected back into the two public documents, and §14 of the architecture — which
lists everything else outstanding — does not mention it.

**This is the single largest exposure in the audit**, because the sentence that markets it is
specifically an argument that it is *not* aspirational.

### A2 · Stock, ordering and the ledger do not exist

`README.md`'s deterministic-core table lists:

- **The ledger** — *"Meters spend against a hard ceiling, and writes every decision to the public log"*
- **Stock and ordering** — *"Parts, shortages, and drafted purchase orders — exposed to the agents as MCP tools"*

Neither is implemented. `grep -ri ledger` over `web/src` finds only a UI label in
`StepCard.tsx`; there is no metering, no ceiling, no public log writer, no parts graph and no
PO drafting.

The consequence is in `SCRIPT.md` shot 24 — the unedited 35-second single take the script calls
*"the single highest-scoring 35 seconds in the submission"*. Its beat sheet is: final step
passes → record seals → **stock decrements → shelf drops below its floor → a purchase order
drafts → the ledger updates** → Cloud Trace. Four of those six beats have no implementation.
The shot cannot be filmed as written today.

`README.md`'s Evidence table also promises *"Purchase orders drafted"*, *"Cost per job, by
strictness"* and *"Total spend"* as fill-from-the-running-system numbers.

### A3 · Model Armor is enabled but never called

`docs/architecture.md` §8 is a genuinely good piece of work — a live experiment against a real
project on 18 Aug, with a benign parts label as the control, and three configuration traps
documented. All of that is real.

What does not exist is any code that calls it. `modelarmor.googleapis.com` appears exactly once
in the repository, in `infra/bootstrap.sh`, as an API enablement. `MODEL_ARMOR_TEMPLATE` is
defined in `.env.example` and read by nothing. No capture, no Scoper turn and no Instructor
transcript passes through a Model Armor call on any surface.

`SCRIPT.md` shots 22c–22e stake the *Trying to cheat it* section on the phone showing
`CAPTURE REJECTED · prompt injection detected in evidence · HIGH`, described as *"real and it is
tested"*, and `rules.md:95` requires the project to function as depicted in the video. The
template check is real; the product path is not wired.

### A4 · Strictness is a four-knob dial with one knob

`docs/architecture.md` §4 defines strictness as *"one configured value moves four knobs
together"*: `min_confidence`, `corroboration_required`, `max_add_fields`, `skeptic_sample_rate`.
`README.md` sells the same idea as *"Buy the assurance you need... Strictness is one dial"* with
a cost row from cents to dollars.

In code, only `max_add_fields` exists — and it is authored per step in the procedure fixtures,
not derived from strictness. `min_confidence`, `corroboration_required` and
`skeptic_sample_rate` appear in no source file. `strictness` is a **required** field on
`procedure.schema.json` and `job.schema.json` that nothing reads.

The axis that *is* implemented is **tier** (`browser` / `app` / `instrumented`), in
`web/src/data/source.ts` and `seal.ts`, governing which provenance classes a surface can reach.
Tier is the load-bearing concept in the product and appears in neither document's strictness
section.

### A5 · Gemma and Veo are named but unused

`README.md` and `docs/architecture.md` §11 both list **Gemma** for volume classification and
**Veo** for the adversarial corpus.

- Veo: zero occurrences in the repository.
- Gemma: `SCREENING_MODEL=gemma-3-4b` sits in `.env.example` and is read by nothing. The only
  other occurrence is `web/src/data/fixtures/scripts.ts`, where `"gemma-3-4b"` is a **label on a
  scripted demo verdict**. `agents/warrant/model.py` has one model, `gemini-3.5-flash`.

`STRATEGY.md` §2 counts Gemma and Veo as 0.4 of the 1.0 bonus and flags *"Find the third"* as
the cheapest point on the board. As it stands the count of additional Google models genuinely in
the live path is zero — though `scripts/gen_task_images.py` really does call
`gemini-2.5-flash-image`, which is an unclaimed one.

### A6 · The physical half of the gate does not exist

`README.md`: *"its hold is physical, not a notification. The keys are in a safe the relay
controls. A held machine is a drawer that does not open."* `SCRIPT.md` shots 25–28 are built on
the safe not opening.

`firmware/` contains only `warrant_reference_instrument.ino` — the BLE peripheral. There is no
relay code anywhere in the tree; `grep -ri relay` finds only the README sentence and two lines in
`specs/2026-08-18-development-lifecycle-design.md`, one of which already flagged it on 18 Aug:

> | 9 | Gate relay unscheduled anywhere | **G1, beside the instrument spike** | It is the ranked #1 proof and the film's money shot |

Three days later it is still unscheduled. `STRATEGY.md` §5 ranks *"a machine held back from
service by the Gatekeeper"* as outcome #1, *"The money shot."*

## B. Documents that contradict each other

### B1 · `SCRIPT.md` names the wrong agent framework, in both scored beats

This is the highest-consequence doc error in the repo, because `SCRIPT.md` itself explains why:

> **Must name the Gemini model and the agent framework, clearly and out loud.** Devpost's own
> guidance is *"say them clearly, don't bury them."*

Both places it does so name the wrong one:

| Where | Text |
|---|---|
| Shot 15, lower third at 0:52 | `Scoper · Gemini 3.5 Flash · Agent Development Kit` |
| Shot 29, VO at 3:19 | *"Seven agents on the Agent Development Kit, every one of them Gemini 3.5 Flash."* |

`README.md`, `docs/architecture.md` §11 and `agents/requirements.txt` all say **Google GenAI
SDK** (`google-genai>=2.19`), and commit `92d3d92` is titled *"Call Gemini 3.5 through the GenAI
SDK"*. There is no ADK dependency anywhere. `SCRIPT.md`'s own note says *"Check both against
`README.md` on the day you shoot"* — this is that check, failing.

### B2 · The front brake procedure has three different step counts

| Source | Steps |
|---|---|
| `README.md` worked example (`front-brake-service · v3`) | **5** |
| `SCRIPT.md` shots 17, 18, 21 (*"Step 1 of 7"*, *"the original seven steps"*) | **7** |
| `web/src/data/fixtures/procedures.ts` → `proc_front_brake_v3` | **4** |

`SCRIPT.md` already flags the *unit* mismatch on the same procedure — README's `90.4°` vs the
architecture's `within(26, 30, "Nm")` vs the shot's bare `28.4` — and asks for one quantity to be
picked. That is still open, and the step count is the same problem unnoticed.

### B3 · Agent count and test counts are stale in four places

| File | Says | Actual |
|---|---|---|
| `STRATEGY.md` §2 | *"five agents over a deterministic core"* | 7 |
| `scripts/smoke.sh` header, step 6 | *"the five agents obey their contracts"* | 7 |

| `android/README.md` | *"17 unit tests, lint clean"* | **128** `@Test` methods across 16 files |

`STRATEGY.md` is git-ignored and internal, so its staleness costs nothing directly — but it is

being built.

### B4 · `android/README.md` lists Google sign-in as not built

Its *What is real and what is scripted* table puts **Google sign-in** under *"Not built yet"*.
This is the `google-sign-in` branch; `auth/GoogleAuth.kt` implements Credential Manager sign-in
in full, with `SignInGate.kt` and `IdentityStore.kt` beside it and an `IdentityPersistenceTest`.
`README.md` markets sign-in as the entire tenancy model. Same table lists *"the network layer"*
as not built, which is still true.

### B5 · The web dashboard described in §9 does not exist — and its screens are on Android

`docs/architecture.md` §9 describes *"The dashboard — five screens"*, on the web, behind Google
sign-in: Procedures, Jobs, The record, Tasks, Technicians, Sign-in. The app, by contrast, is
*"where evidence is made"*.

Deployed web routes (from a clean `npm run build`): `/`, `/about`, `/firmware`, `/job/[id]`,
`/library`, `/model-tests`, `/model-tests/[...id]`, `/r/[id]`. There is no procedures screen, no
jobs list, no tasks screen and no technicians screen.

Those screens exist in the **Android** app: `ui/ProceduresScreen.kt`,
`ui/procedure/CreateProcedureScreen.kt`, `ui/records/RecordsScreen.kt`,
`ui/settings/SettingsScreen.kt`, `ui/account/AccountScreen.kt`.

§13 predicted exactly this as the last cut — *"**the dashboard entirely**, with the Scoper moving
onto the phone"* — so the plan worked. §9 was simply never rewritten, and it is still present
tense. Four shipped web routes (`/about`, `/library`, `/firmware`, `/model-tests`) are documented
in no architecture section at all.

### B6 · The cut order was executed in reverse

`STRATEGY.md` §6: *"Cut order when it slips: Wright → MCP surface → second procedure → …"*

Wright, first to cut, is fully built: `agents/warrant/wright.py`, `contract/agents/wright-turn.schema.json`,
7 eval scenarios, and its own 484-line design spec. MCP, second to cut, is gone. Not a defect —
Wright is `STRATEGY.md` §5's *"most striking single demo"* — but the strategy document no longer
describes the plan being executed, which matters for the next cut decision.

### B7 · Minor: the two pickers disagree by one note

`android/.../ui/PublicTasks.kt` states it mirrors `web/src/app/page.tsx` *"same order, same
names, same notes, same artwork"* and that a divergence breaks the surface comparison. All five
tasks match except the brake note: web adds *"Open it to see this browser refused."* The
difference is correct per-surface behaviour — it is the stated invariant that needs relaxing,
not the string.

## C. Documents versus the deployed project

All four verified live today against `warrent-505918`.

### C1 · No Firestore ruleset is released

```
GET firebaserules.googleapis.com/v1/projects/warrent-505918/releases  →  {}
```

Two rulesets were uploaded on 20 Aug (`5e28f2e4…`, `1109c612…`). Neither is released, so the
live database is not running `firestore.rules` at all.

`README.md`: *"**Tenancy is enforced by Firestore itself**."* `docs/architecture.md` §11:
*"Firestore — tenancy enforced by rules, not by application code (§8)."*

The emulator test behind §8 is real and is good engineering. The claim as written is about the
product, not the test, and in the deployed project it is currently false. `infra/deploy-rules.sh`
exists and publishes a release; it has not completed successfully against this project.

### C2 · The deployed revision runs on the default compute service account

```
warrant-00001-rsd  →  1020487917587-compute@developer.gserviceaccount.com
```

`README.md`: *"`deploy-web.sh` attaches a least-privilege service account (`firebaseauth.admin`
… `datastore.user`) … There is no long-lived secret to leak, rotate, or commit."*

The script genuinely does pass `--service-account "$RUN_SA"`, and
`warrant-web@warrent-505918.iam.gserviceaccount.com` exists. But the only revision in the
service predates that change, so the paragraph is true of the script and false of what is
running. The no-key half of the claim holds either way.

### C3 · The deployed service has no auth layer

```
GET https://warrant-zq2l2kwg3q-uc.a.run.app/api/auth/session  →  404
```

The live image is `web:20260819-234815`, two days behind the branch. `README.md` says *"Once it
is on, the identity model in `docs/architecture.md` §7 is live."* It is not, on the deployed
host. `docs/architecture/Architecture.html` independently records the same thing, plus
*"Authorized domains — 3 listed — the Run host is not one"*, so sign-in would still be refused
from that origin after a redeploy until `deploy-web.sh`'s authorisation step runs.

A redeploy from this branch likely fixes C2 and C3 together.

### C4 · Cloud Scheduler is not enabled, and bootstrap does not enable it

`docs/architecture.md` §11 lists *"Cloud Scheduler → Cloud Run `/api/tasks/sweep`, one cron for
every tenant."* `cloudscheduler.googleapis.com` is not enabled on the project and is not in
`infra/bootstrap.sh`'s enablement list. The `/api/tasks/sweep` route exists and builds; nothing
calls it on a schedule.

Pub/Sub is enabled with **0 topics** — consistent with §14, which already says the subscriber
does not exist.

The deployed site serves `FixtureSource` with `fabricated = true`, which is labelled in-product
and honest; noting it only because `README.md`'s Evidence table is to be filled *"from the
running system"*.

## D. Things that break for anyone following the README

### D1 · `./scripts/smoke.sh` fails

`README.md` presents `./scripts/smoke.sh` as *the* verification command. Step 6/7 runs
`python3 -m evals check`, which **exits 1**:

```
66 scenarios load, 7 agents, 209 assertion groups
13 cannot be built:
  inspector/tread-depth-passes: tyre/tread-coin-deep.jpg is not in .../evals/media
  skeptic/same-asset-belongs: asset/bike-a-fork.jpg is not in .../evals/media
  … 11 more
```

The `tyre/` and `asset/` media directories do not exist; `torque/` holds 1 of the 4 files its
scenarios reference. Under `set -euo pipefail` the script aborts there, before the Playwright
funnel. Steps 1–4 all pass when run individually, so this is one broken gate, not a broken suite.

### D2 · The error points at a script that has never existed

`agents/warrant/base.py:112` raises `"{ref} is not in {MEDIA_DIR}; run evals/gen_media.py"`.
There is no `evals/gen_media.py` and there never has been — the nearest thing is
`scripts/gen_task_images.py`. Meanwhile nine generated images sit in `agents/evals/media/unfiled/`
waiting to be filed into the slots the scenarios name.

### D3 · The tenancy proof silently skips on the JDK the repo tells you to install

`scripts/smoke.sh` step 5 needs a **JDK 21+** for the Firestore emulator and prints
`skipped — needs a JDK 21+` otherwise. `android/README.md` says *"Requires JDK 17"*. This machine
has JDK 17, so the strongest claim in the README — *"proved by running `firestore.rules` in the
Firestore emulator, not by asserting it"* — prints "skipped" on a machine set up per the repo's
own instructions. The skip is deliberate and reasoned in the script comments; it just needs to be
loud, because a silent skip and a pass read identically in a scroll-back.

## E. Smaller items

- **`sealJob` writes three undeclared keys.** `web/src/data/seal.ts:52` spreads
  `verificationCeiling(job.tier)` — which returns `{tier, reachable, unreachable}` — and *then*
  sets `ceiling_tier` / `ceiling_reachable` / `ceiling_unreachable` separately. Only the
  `ceiling_*` trio is in `record.schema.json`, so every sealed record carries three extra fields
  the contract does not declare. The `as SealedRecord` cast at the end is what suppresses the
  error.
- **`docs/data-model.md` indexes a collection the rules do not cover.** Its index table lists
  `nodes`; `firestore.rules` covers `spec_nodes`, `spec_values`, `spec_docs` and `spec_chunks`
  but not `nodes`.
- **Spec'd but never built** (expected in dated design docs, listed because one is load-bearing):
  `web/scripts/storage-rules.test.mjs`; `scripts/deploy.sh`; and
  `android/…/instrument/BleProxy.kt`, which `specs/2026-08-19-wright-design.md` calls *"The film
  shot"* and which `SCRIPT.md` shots 23e–23f depend on.
- **Not a finding, checked and cleared:** §8's *"65 assertions"* looked wrong at 33 literal
  `assertFails`/`assertSucceeds` calls, but they run inside loops over identity corpora, so 65 at
  runtime is plausible. Unverified here only because the emulator needs a JDK this machine lacks.
- **Project id is `warrent-505918`** — a typo baked into the real project. Cosmetic, and it will
  appear in any console screen recording, including `SCRIPT.md` shots 29–30.

## What to do first

Ordered by cost-to-fix against exposure, not by severity alone.

1. **Fix `SCRIPT.md`'s framework name** — two strings, and they are the two beats Devpost tells
   judges to look for. Ten minutes. *(B1)*
2. **Redeploy from this branch.** Almost certainly clears C2 and C3 together and re-runs the
   domain authorisation step.
3. **Run `./infra/deploy-rules.sh` to a successful release.** Until it does, the README's
   headline tenancy claim is false of the live project. *(C1)*
4. **Generate or file the 13 missing media files**, and fix the `gen_media.py` reference in
   `base.py:112`, so `smoke.sh` passes end to end. *(D1, D2)*
5. **Decide MCP: build a thin one, or unclaim it.** A read-only server over the existing
   `DataSource` would satisfy most of the seven tools; otherwise the two paragraphs that call it
   load-bearing have to come out of `README.md` and §9. *(A1)*
6. **Reconcile SCRIPT shot 24 with what exists.** Either build stock/ledger, or re-cut the chain
   around seal → gate → hold, which does exist and is deterministic. *(A2)*
7. **Rewrite §9 for the surfaces that shipped**, and note that the dashboard moved to the phone
   as §13 planned. *(B5)*
8. **Pick one quantity for the brake procedure** — value, unit and step count — and make README,
   SCRIPT and the fixture agree. *(B2)*
9. Stale counts: five→seven agents, 62→66 scenarios, 17→128 tests, sign-in out of *not built*.
   *(B3, B4)*

Items 1–4 and 9 are a morning. Items 5 and 6 are scope decisions, and `STRATEGY.md` §7's warning
applies to both: *"cut further without guilt"* — but cut the claim at the same time as the code.
